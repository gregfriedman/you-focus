# ADR: Split content script into modules 

## Context and Problem Statement
We started with all the javascript content script code in a single file. But this made it difficult to write and run unit tests. It also made it more difficult to understand how the code worked. And it made us less careful with thinking through separation of responsibilities. 

Unfortunately, browser extension content scripts don't natively support ES module syntax so the easiest path was just to put it all in a single file.

## Considered Options
- Single file without unit tests
- ES Modules bundled using esbuild
- ES Modules imported using dynamic import

## Decision Outcome
Decided to use ES Modules bundled with esbuild so that we could cleanly separate the content script code and import into unit tests.

Rejected loading the modules via dynamic `import()` with `web_accessible_resources` because Safari support is unconfirmed and web_accessible_resources can be used by websites to build a fingerprint of the user which we should avoid to preserve privacy as best we can.

### Consequences
- Pro: can use vitest to import functions and run unit tests 
- Pro: code is separated by responsibility
- Pro: main script is much shorter and easier to understand
- Con: requires build step before running e2e test or updating unpacked extension in the browser
- Con: more complicated build process and tooling
- Con: code running in the browser is different from written code
