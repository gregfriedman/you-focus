# ADR: Use Ramda

## Context and Problem Statement
Much of what we're doing in code is actually transforming data from one shape to another. And those transformations can be expressed as a sequence of common, simple operations that gradually rework that starting shape to the ending shape (like map and filter). Since the intermediate values aren't meaningful, we can eliminate that noise using point-free style via curried functions.

For example:
```js
// return `include` array of the truthy property names and `exclude` array of the falsy ones
  return R.pipe(
    // { a: true, b: false, c: true }
    R.partition(Boolean), // [ {a: true, c: true}, { b: false} ]
    R.zipObj(['include', 'exclude']), // { include: { a: true, c: true }, exclude: { b: false } }
    R.map(R.keys), // { include: [ 'a', 'c' ], exclude: ['b' ] }
  )(settings)
```

## Considered Options
- Vanilla js with hand coded transformation functions
- Lodash/fp library
- Ramda library

## Decision Outcome
Decided to use Ramda because it does tree shaking well so can avoid unnecessary bloat in the bundle. Also, some of its operations handle objects in addition to collections so we can build more transformations from the same primitives. And I've always been interested in learning it because it was functional first and seems to offer a lot of additional operations over what I've used in the past.

Opted not to use Lodash/fp because it doesn't tree shake well and so we could end up with the whole lodash library in the bundle.

Opted not to use vanilla js because we'd be recreating so much existing and well tested code.

### Consequences
- Pro: pipe() cleanly describing the sequence of operations
- Pro: curried functions so the pipeline doesn't have to give a name to the input argument
- Con: 3rd party dependency that could introduce vulnerability
- Con: learning-curve
- Con: doesn't have some of lodash's niceties like 
  - overload of string vs function (e.g. `_.map('firstName', [])`)
  - `_.isEmpty(null) => true`
